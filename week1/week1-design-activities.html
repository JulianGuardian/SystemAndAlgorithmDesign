Concepts Quiz · Scale Estimation · Whiteboard Practice

⚡ Part A — Concepts Quiz

Question 1

Which requirement is NON-functional?

  • Users can post a tweet
  • Users can follow other users
  • The API must respond in under 200ms for 99% of requests
  • Users can search by hashtag
Response latency is a non-functional requirement — it describes how well the system performs, not what it does. Options A, B, D describe features the system offers (functional).
Question 2

A service promises 99.9% availability. Approximately how much downtime is allowed per year?

  • ~1 hour
  • ~8.7 hours
  • ~44 hours
  • ~87 hours
99.9% = 0.1% downtime. 0.001 × 365 × 24 = ~8.76 hours per year. 99.99% = ~52 min/year. 99.999% ("five nines") = ~5 min/year.
Question 3

In the 6-step framework, what should you do IMMEDIATELY after clarifying requirements?

  • Choose the database
  • Estimate the scale (QPS, storage)
  • Draw the architecture diagram
  • Define the API endpoints
Estimate scale — knowing the QPS and storage requirements directly determines whether you need caching, sharding, CDN, etc. Every architecture decision flows from scale.
Question 4

What does "horizontally scalable" mean?

  • You handle more load by adding more servers of the same type
  • You handle more load by adding more RAM/CPU to a single server
  • The system scales only for read traffic, not writes
  • The system replicates data across geographic regions
Horizontal scaling (scale out) = add more machines. Vertical scaling (scale up) = bigger machine. Horizontal is preferred for large-scale systems because it has no single-machine ceiling.
Question 5

A service has 10M DAU, each making 5 API requests per day. What is the approximate QPS?

  • ~58 QPS
  • ~580 QPS
  • ~580 QPS
  • ~5,800 QPS
10M × 5 = 50M requests/day. 50M ÷ 86,400 sec ≈ 578 QPS ≈ 580 QPS. Rule of thumb: 1M requests/day ≈ 12 QPS.

🧮 Part B — Estimation Workshop (In-class)

Work in pairs. For each scenario, estimate the required numbers. Show your work (don't just write the answer).

Scenario 1 — Photo sharing app (like Instagram)

  • 50M DAU. Each user views 20 photos/day and uploads 1 photo/week.
  • Average photo size: 2 MB compressed.
  • Estimate: (a) read QPS, (b) write QPS, (c) storage per year.

Scenario 2 — Chat application (like WhatsApp)

  • 200M DAU. Each user sends 40 messages/day. Average message = 100 bytes.
  • Messages must be delivered in under 1 second.
  • Estimate: (a) messages/sec, (b) storage per year (text only), (c) what makes this design hard vs. a URL shortener?

🖊️ Part C — Whiteboard Practice

Using the 6-step framework, spend 15 minutes designing a simple "Pastebin" (text paste sharing) service in pairs. One person explains, one draws. Then swap roles and critique.

Pastebin requirements (use these):

  • Functional: User pastes text → gets a short URL. Anyone with the URL can read the paste. Pastes expire after 24h by default.
  • Non-functional: 10M pastes/day. Reads 10× more common than writes. Paste max size = 1MB. 99.9% availability.

Design Checklist

  • Did you list functional AND non-functional requirements before drawing?
  • Did you estimate QPS and storage before choosing a database?
  • Did you draw: client, load balancer, app server, database?
  • Did you identify at least one bottleneck and propose a solution?
  • Did you define at least two API endpoints (create paste, get paste)?

📝 Part D — Weekly Reflection

  1. Research: what is the difference between latency and throughput? Give a real-world analogy for each.
  2. Calculate: if a data center has 99.95% availability, how many minutes of downtime are allowed per month?
