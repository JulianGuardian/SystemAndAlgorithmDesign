Introduction to System Design

What is system design · The technical interview process · How to approach a design question

🎯 Learning Objectives

  • Understand what "system design" means in the context of a technical interview.
  • Identify the key pillars of a scalable system: scalability, reliability, availability, and maintainability.
  • Follow a structured framework for answering any system design question.
  • Estimate the scale of a system using back-of-the-envelope calculations.
  • Read and draw basic architecture diagrams using standard component boxes.

🏗 1 · What Is System Design?

System design is the process of defining the architecture, components, interfaces, and data of a system to satisfy specified requirements. At a tech company, system design interviews test whether you can think at scale — designing systems that handle millions of users, terabytes of data, and thousands of requests per second.

The two kinds of interviews you will face:
Coding interview — algorithmic problem on a whiteboard or editor. Focus: correctness, complexity, clean code.
System design interview — open-ended design question (e.g., "design Twitter"). Focus: scale, trade-offs, component selection, and communication.

Why Companies Care About System Design

Algorithms tell a company you can write efficient code. System design tells them you can build products — products that don't fall over at 3AM when they go viral, that can be extended by a team of 50 engineers, and that can recover from hardware failures automatically.

The Four Pillars of a Good System

PillarQuestion it answersExample
ScalabilityCan it handle 10× more users tomorrow?Add servers behind a load balancer

📋 2 · The 6-Step Interview Framework

Every system design question can be answered with the same structured approach. Practice this until it is automatic.

  • Clarify requirements (3–5 min): Ask what features are in scope. Functional (what it does) vs. non-functional (scale, latency). Never assume — ask.
  • Estimate scale (2–3 min): How many users? DAU (Daily Active Users)? QPS (Queries Per Second)? Storage per year? Write these on the board.
  • Define the API: What are the core endpoints the system exposes? (e.g., POST /shorten, GET /:code). This anchors everything else.
  • High-level design: Draw the main boxes — clients, servers, databases, caches. Connect them with arrows. Start simple.
  • Deep dive into components: Pick 1–2 components and go deep. Database schema, caching strategy, partitioning approach.
  • Identify bottlenecks and trade-offs: Single points of failure? Hot partitions? Consistency vs. availability? Propose solutions.
💡 Interview tip: Interviewers do not expect a perfect design. They want to see your thought process. Communicate every assumption out loud. When you make a trade-off, name it ("I'm choosing eventual consistency here because…").

🧮 3 · Back-of-the-Envelope Estimation

Knowing the scale of a system guides every architecture decision. Before you place any box on the board, estimate the load.

Key Numbers to Memorize

UnitApproximate value
L1 cache latency0.5 ns
RAM access100 ns
SSD read100 μs (1,000× slower than RAM)
Network round-trip (same DC)0.5 ms
Network round-trip (cross-continent)150 ms
1 GB RAM≈ 10⁹ bytes
1 million seconds≈ 11.5 days

Example: Estimate a URL Shortener

Assumptions: 100M DAU. 10% write (shorten), 90% read (redirect). Average URL = 100 bytes.

QPS: 100M users × 1 request/day ÷ 86,400 sec ≈ ~1,200 QPS (reads ≈ 1,080 QPS, writes ≈ 120 QPS)
Storage (10 years): 120 writes/sec × 86,400 × 365 × 10 × 100 bytes ≈ ~3.8 TB

Conclusion: read-heavy (9:1), modest write QPS, storage fits on a few servers. → Cache reads heavily, scale reads horizontally.

✅ 5 · Functional vs. Non-Functional Requirements

Every design question starts with clarifying requirements. Confusing these two categories is a common interview mistake.

Functional requirements — what the system does:
• Users can shorten a URL
• Users can retrieve the original URL from a short code
• Links expire after 30 days (optional)

Non-functional requirements — how well it does it:
• Redirect latency < 100ms (p99)
• 99.99% availability (≤ 52 minutes downtime/year)
• Horizontally scalable to handle 1M QPS
• Short codes must be unique (no collisions)
Interview practice: When given any system (Twitter, WhatsApp, Uber) spend the first 3 minutes writing two lists on the board: Functional and Non-Functional. This shows discipline and prevents you from designing the wrong system.
