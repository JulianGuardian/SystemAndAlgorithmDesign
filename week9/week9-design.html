Core Components

Block Server — splits files into fixed-size chunks (e.g., 4 MB), computes SHA-256 of each chunk, deduplicates, and uploads only new/changed chunks to blob storage.

Blob Storage — Amazon S3, Google GCS, or Azure Blob. Immutable, infinitely scalable, cheap per GB. Stores raw file chunks.

Metadata Database — relational DB (MySQL + read replicas) storing file name, path, owner, chunk references, version history, sharing permissions.

Sync Service — notifies clients of changes via WebSocket or long-polling. Broadcasts delta changes, not full files.

Chunked Upload Flow

Chunking solves reliability: if a 500 MB upload fails at 490 MB, only the last chunk must be re-uploaded, not the entire file.

Amazon S3 Key Concepts

Bucket — top-level namespace, globally unique name, tied to a region.
Object — immutable blob of data, up to 5 TB. Stored with a key (path-like string).
Versioning — bucket-level setting. Keeps all versions of an object; delete marker instead of deletion.
Presigned URL — time-limited URL granting access to a private object without exposing credentials. Used for direct client uploads/downloads, bypassing your server.
Design tip: For large uploads, use S3 Multipart Upload — upload parts in parallel, then commit. Equivalent to chunking on the client side. Parts can be retried individually.

🔄 3 · Consistent Hashing

The Problem with Naive Modulo Hashing

With N servers, naive assignment is server = hash(key) % N. If you add or remove a server, N changes → nearly ALL keys map to different servers. A cache becomes useless; a storage cluster must shuffle petabytes of data.

The Solution: A Hash Ring

Place all possible hash values on a circle (ring). Each server is assigned a position on the ring. A key maps to the first server clockwise from its hash position. Adding a server only reassigns keys between the new server and its predecessor — O(K/N) keys, not all K keys.

Virtual Nodes

A single server position can cause uneven load. Virtual nodes: each physical server is represented by multiple ring positions (e.g., 150 virtual nodes each). This distributes load more evenly and balances the impact of node addition/removal.

Used in practice: Amazon DynamoDB (partition key hashing), Apache Cassandra (token ranges), Memcached client libraries (ketama algorithm), Nginx upstream consistent hashing module.

🗄️ 5 · File Metadata & Search

Schema Design

files: file_id (PK), owner_id, name, path, size_bytes, checksum_sha256, created_at, updated_at, is_deleted, version_count

file_chunks: chunk_id (PK), file_id (FK), chunk_index, blob_url, size_bytes, checksum

file_shares: share_id, file_id, shared_with_user_id, permission (view/edit), expires_at

Why Separate Blob Store from Metadata DB?

Relational databases are optimized for structured queries and transactions, not storing gigabytes of raw bytes. A dedicated blob store (S3) handles binary data with built-in replication, CDN integration, and cost-efficient tiering. The metadata DB stays small and fast for queries like "list all files in folder X".
