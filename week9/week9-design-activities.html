⚡ Part A — Quiz

Question 1

What is the PRIMARY benefit of chunked file uploads in a system like Google Drive?

  • Chunks are encrypted individually, improving security
  • Smaller chunks compress better, saving storage
  • Resumability — only changed/failed chunks need to be re-uploaded, not the entire file
  • Chunking enables parallel encryption keys per chunk
Resumability and delta sync. If a 1 GB upload fails at 900 MB, only the last chunk is re-sent. Also, when a file is edited, only changed chunks are uploaded — not the whole file. Deduplication (same chunk across multiple files stored once) is an additional bonus.
Question 2

Consistent hashing primarily solves which problem?

  • Encrypting data at rest in distributed storage
  • Minimizing key redistribution when servers are added or removed
  • Ensuring ACID transactions across nodes
  • Reducing network latency between servers
Key redistribution. With naive modulo hashing, changing N causes nearly all keys to remap. Consistent hashing on a ring means only K/N keys move when a server is added or removed — a dramatic improvement for cache and storage clusters.
Question 3

What is the purpose of virtual nodes in consistent hashing?

  • To distribute each physical server across multiple ring positions for more even load distribution
  • To create backup servers that take over during failures
  • To encrypt keys at multiple ring positions
  • To reduce the number of hash computations needed
Load distribution. With a single position per server, one server might own a large arc of the ring (holding more keys). Virtual nodes (e.g., 150 per server) spread each server across the ring, giving a more even distribution. They also smooth out the impact of adding/removing a server.
Question 4

You need to store 5 billion product images for an e-commerce site. Each image is write-once, never updated. Which storage type is most appropriate?

  • Block storage (EBS) — fastest random access
  • File storage (NFS) — familiar filesystem interface
  • Object storage (S3) — immutable objects, cheap at scale, CDN-friendly
  • Relational database — easy querying by product ID
Object storage. Images are immutable (write-once), there are billions of them, and they integrate natively with CDNs via presigned URLs. S3-class storage is orders of magnitude cheaper per GB than block or file storage at this scale.
Question 5

Google Docs uses Operational Transform for conflict resolution. What makes this approach different from Dropbox's "conflict copy"?

  • OT uses a central server to serialize all writes; conflict copy allows concurrent offline writes
  • OT merges concurrent edits automatically without user intervention; conflict copy requires the user to manually merge two file versions
  • OT is simpler to implement but has lower conflict resolution accuracy
  • OT only works for binary files; conflict copy works for text
Automatic merge vs manual merge. OT transforms concurrent insert/delete operations against each other, allowing two users to type simultaneously without conflicts. It's extremely complex to implement correctly. Dropbox's conflict copy is simpler: both versions survive and the user sees them side-by-side.

🖊️ Part B — Design Workshop: Build Google Drive

Walk through the 6-step system design interview process for Google Drive. Work in pairs: one person drives, one asks clarifying questions.

1
Clarify Requirements (3 min)
Functional: Upload/download files, sync across devices, share with permissions, versioning?
Non-functional: What's the maximum file size? How many users? What availability SLA?
Out of scope: Real-time collaborative editing (Google Docs feature, not Drive itself).
2
Capacity Estimation (2 min)
500M users, 10% DAU (50M). Average 10 upload actions/day per DAU = 500M uploads/day.
500M / 86,400 ≈ 5,800 uploads/sec. Average file 1MB → 5.8 GB/sec write throughput.
5-year storage: 500M × 15GB × 0.3 (compression) = ~2.25 EB.
3
API Design (2 min)
POST /files/upload — initiate chunked upload, returns upload_session_id
PUT /files/upload/{session_id}/chunks/{idx} — upload a single chunk
POST /files/upload/{session_id}/complete — finalize, assemble chunks
GET /files/{file_id} — get metadata + download URL
GET /files/{file_id}/versions — list versions
4
High-Level Design (5 min)
Draw: Client → Load Balancer → API Servers → Block Server (chunking + dedup) → Blob Storage (S3).
Metadata: MySQL with read replicas. Cache: Redis for file metadata hot reads.
Sync: WebSocket server (or Server-Sent Events) for real-time change notifications.
5
Deep Dive: Sync Service (3 min)
How does Device B know Device A uploaded a new file version?
Options: polling (simple, high load), long-polling, WebSockets (bi-directional), Server-Sent Events (one-way push).
At scale: separate notification service (similar to Week 6 design).
6
Failure & Scale (2 min)
Blob storage failure → S3 has 11 nines durability (multi-zone replication built-in).
Metadata DB failure → primary-replica failover; read replicas for query scale.
Block server bottleneck → stateless, horizontally scalable; dedup index in Redis.

🤝 Part C — Extension: Add Sharing & Collaboration

Your Google Drive design from Part B supports personal file storage. Now extend it to handle file sharing and collaborative access.

Scenario: Shared Folder with 10,000 collaborators

A university creates a shared Drive folder for all students. 10,000 students can read files; 50 faculty can upload/edit. Design the permission model and the notification flow when a faculty member adds a new file.

Questions to answer:

  • How do you model permissions? (ACL table? Role-based?)
  • When a faculty member uploads a file, do you notify all 10,000 students? (Fan-out problem!)
  • How does your sync service scale to 10,000 concurrent WebSocket connections for one folder?

🔍 Part D — Peer Review Checklist

  • Chunking strategy defined — chunk size justified (e.g., 4–8 MB) and resumability explained?
  • Blob storage separated from metadata DB with a clear reason?
  • Consistent hashing explained with a concrete benefit (not just "it balances load")?
  • Sync notification mechanism named (WebSocket/SSE/long-poll) and its trade-offs acknowledged?
  • Storage scale estimated (not just "a lot of data") — actual numbers in PB/EB?
  • At least one failure scenario addressed (blob storage down, metadata DB failover)?

📝 Part E — Weekly Reflection

  1. Dropbox uses a content-addressable store (chunks are named by their SHA-256 hash). How does this enable global deduplication across ALL users' files — not just within one user's account?
  2. Research: how does S3 achieve 11 nines durability (99.999999999%)? What replication strategy does AWS use internally?
  3. Design a "recycle bin" feature for Google Drive: files deleted by a user are recoverable for 30 days. What schema changes are needed, and how do you handle storage cost for deleted files?
