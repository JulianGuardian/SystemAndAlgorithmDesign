⚡ Part A — Quiz

Question 1

A URL shortener uses base62 encoding with 7 characters. How many unique short codes are possible?

  • 62 × 7 = 434
  • 62 + 7 = 69
  • 62⁷ ≈ 3.5 trillion
  • 26⁷ ≈ 8 billion
Base62 uses 62 characters (a-z, A-Z, 0-9). With 7 positions: 62⁷ = ~3.52 trillion unique codes. At 1,160 writes/sec for 10 years = ~366 billion total → more than enough headroom.
Question 2

Why would you choose a 302 redirect over a 301 for a URL shortener?

  • 302 is faster because browsers cache it
  • 302 ensures every redirect hits your servers so you can track analytics
  • 302 is required by HTTP/2
  • 301 does not work with shortened URLs
Analytics — 301 (permanent) is cached by browsers; subsequent clicks bypass your server, so you lose click count data. 302 (temporary) ensures every redirect is processed by your service, enabling click tracking.
Question 3

The Token Bucket rate limiter allows burst traffic. The Leaky Bucket does NOT. Why?

  • Token Bucket accumulates unused tokens; Leaky Bucket processes at a constant output rate
  • Token Bucket uses more memory
  • Leaky Bucket allows burst at the start of each minute
  • They are equivalent — both allow the same burst
Token Bucket: if a user doesn't make requests for 5 minutes, tokens accumulate (up to bucket capacity). When they burst, they use stored tokens → allowed. Leaky Bucket: output is always a constant drip rate — excess requests wait in queue or are dropped immediately.
Question 4

A mobile app shows a user's feed (posts + author profiles + like counts). Which technology reduces over-fetching better?

  • REST with versioned endpoints
  • GraphQL — client requests exactly the fields it needs
  • REST with pagination
  • WebSockets
GraphQL — the client query specifies exactly which fields (post.text, author.name, likeCount) without fetching the entire user/post objects. This is critical for mobile clients with limited bandwidth.
Question 5

What HTTP status code should a rate limiter return when a client exceeds its limit?

  • 400 Bad Request
  • 401 Unauthorized
  • 429 Too Many Requests
  • 503 Service Unavailable
429 Too Many Requests — the standard response for rate limiting. Should include a Retry-After header telling the client when to try again. Also include X-RateLimit-Limit and X-RateLimit-Remaining headers for transparency.

🎯 Part B — Mock Interview: URL Shortener (In-class)

This is your primary preparation for the Corte 1 design evaluation. Work in pairs: one is the interviewer, one is the candidate. 15 minutes to design, then swap roles.

Prompt (read to the candidate)

"Design a URL shortening service like Bit.ly. Users should be able to shorten a URL and share the short link. Anyone with the link should be redirected to the original URL."

Then stop. Wait for the candidate to ask clarifying questions.

Interviewer Scoring Rubric

  • (2 pts) Requirements: Candidate asked clarifying questions before designing. Both functional and non-functional requirements identified.
  • (2 pts) Estimation: Candidate calculated QPS and storage before choosing components.
  • (2 pts) API: Defined at least POST /shorten and GET /:code with correct HTTP verbs and response codes.
  • (2 pts) Architecture: Drew at least: LB, app server, Redis cache, DB. Explained why each is present.
  • (1 pt) Short code generation: Explained the method (base62 counter) and why it avoids collisions.
  • (1 pt) Trade-offs: Mentioned at least one trade-off (301 vs 302, sync vs async replication, etc.)

Total: 10 points. Score ≥ 7 = ready for Corte 1.

✏️ Part C — API Design Exercise

Design the REST API for a Pastebin service. Write the endpoints (method + path), request body/params, and HTTP response codes for each operation below:

  1. Create a new paste with text content and optional expiry
  2. Retrieve a paste by its short ID
  3. Delete a paste (authenticated users only)
  4. List all pastes by a specific user (paginated)

For each endpoint: include the URL path, HTTP method, request body/params, and at least two possible response status codes.
