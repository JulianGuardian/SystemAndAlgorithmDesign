🔗 1 · URL Shortener Design

This is the canonical first system design problem. It tests your ability to go from requirements to a complete design covering APIs, storage, short code generation, and scale.

Step 1 — Requirements

Functional: Given a long URL, return a short URL (e.g. bit.ly/aB3xK9). Given a short URL, redirect to original. Links expire after 30 days by default (configurable).

Non-functional: 100M links created/day. Read:Write = 10:1. Redirect latency < 10ms (p99). 99.99% availability. Short codes must be unique (no collisions).

Step 2 — Scale Estimate

Writes: 100M/day ÷ 86,400 ≈ 1,160 writes/sec
Reads: 1,160 × 10 = 11,600 reads/sec
Storage (10 years): 1,160 × 86,400 × 365 × 10 × ~500B ≈ ~1.8 TB
→ Read-heavy, modest write QPS, storage manageable on a few nodes. Cache reads aggressively.

Step 3 — API Design

# Create short URL
POST /api/v1/shorten
Body: { "long_url": "https://...", "expires_days": 30 }
Response: { "short_url": "https://short.ly/aB3xK9" }

# Redirect
GET /{short_code}
Response: HTTP 301/302 redirect to long_url
301 vs 302: 301 (Permanent) → browser caches the redirect, future requests skip the server (less load, but you lose analytics). 302 (Temporary) → every request goes through your server (more load, full analytics). Choose 302 for analytics-critical links.

Step 4 — Short Code Generation

MethodHowProCon

Base62 encoding (a-z, A-Z, 0-9) with 7 characters gives 62⁷ ≈ 3.5 trillion unique codes — more than enough.

📄 2 · Pastebin — Key Differences from URL Shortener

Pastebin stores arbitrary text content (code snippets, logs) and serves it back. The design is similar to a URL shortener but with important differences.

URL ShortenerPastebin
Stored data~500B (URL string)Up to 1 MB (text content)
Content storageRelational DBObject storage (S3) for content; DB for metadata
Read patternRedirect (302)Serve content (200 + body)
ExpiryOptional (30 days)Required (auto-delete content from object store)
Syntax highlightN/ALanguage detection → CDN-cached HTML
Design insight: Separate metadata (paste ID, user, language, expiry, URL to content) stored in PostgreSQL from the content itself stored in S3/object storage. This keeps the DB lightweight and allows content to scale independently.

🚦 3 · Rate Limiting

Rate limiting protects your system from abuse, ensures fair usage, and prevents denial-of-service. It lives in the API gateway or as a middleware layer.

Algorithms

AlgorithmHow it worksAllows burst?Memory
Fixed Window CounterCount requests per fixed time window (e.g., 100/min). Reset at minute boundary.Yes (2× at boundary)O(1)
Sliding Window CounterWeighted sum of current + previous window proportional to elapsed time.PartialO(1)
Token BucketBucket fills at fixed rate (1 token/sec). Each request consumes 1 token. If empty, reject.Yes (burst up to bucket size)O(1) per user
Leaky BucketRequests enter a queue, processed at fixed rate. Queue overflow = reject.NoO(queue size)
Distributed implementation with Redis:
count = INCR(user_id:minute)
if count == 1: EXPIRE(user_id:minute, 60) ← set TTL on first request
if count > limit: return 429 Too Many Requests

🔌 4 · API Design — REST vs. GraphQL

RESTGraphQL
StructureMultiple endpoints, one resource per URLSingle endpoint (/graphql), query specifies shape
Over-fetchingReturns all fields of a resourceClient specifies exactly which fields
Under-fetchingMay need multiple round-trips for related dataFetch nested resources in one query
CachingHTTP caching works naturally (GET /users/42)POST to /graphql — harder to cache
Versioning/api/v1/, /api/v2/ — explicit versionsSchema evolution, deprecate fields in-place
Best forPublic APIs, simple CRUD, mobile where HTTP caching helpsComplex data graphs, dashboards, multiple client types

REST Example — URL Shortener API

# Create
POST   /api/v1/urls              → 201 Created  { "short_code": "aB3xK9" }

# Read
GET    /api/v1/urls/{code}       → 200 OK  { "long_url": "...", "clicks": 142 }

# Redirect
GET    /{code}                   → 302 Found  Location: https://original.url

# Delete
DELETE /api/v1/urls/{code}       → 204 No Content

REST Design Principles

Resource-based URLs: Nouns, not verbs → /users/42/orders not /getUserOrders
HTTP verbs carry action: GET (read), POST (create), PUT/PATCH (update), DELETE (remove)
Status codes: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 404 Not Found, 429 Too Many Requests, 500 Server Error
Stateless: Each request carries all necessary context (auth token in header)
