🐦 1 · Twitter Newsfeed — The Core Problem

Scale: 500M registered users, 100M daily active, some celebrities with 100M+ followers. Users expect their feed to load in <200ms.

The fundamental tension: When a user posts a tweet, do you immediately push it to all followers' caches (fast reads, slow writes), or do you compute the feed on read (slow reads, fast writes)? This write vs. read amplification tradeoff defines the two approaches.
DimensionFan-out on Write (Push)Fan-out on Read (Pull)
Read latencyVery fast — pre-built feedSlower — compute on demand
Write latencySlower — write to all N followersFast — just save the tweet
StorageO(followers) copies per tweetOne copy per tweet
ConsistencyEventual (propagation delay)Strong (always fresh)
Best forRegular users (low follower count)Celebrities (100M+ followers)

📤 2 · Fan-out on Write (Push Model)

When a user tweets, a fan-out service pushes the tweet ID into each follower's feed cache (Redis list). On read, the feed is already populated — just fetch and render.

The Celebrity Problem

If a celebrity with 10M followers tweets, the fan-out service must write to 10M Redis entries. At scale this can take minutes and overwhelm the workers.

Hybrid solution: Apply fan-out on write for regular users (<X followers). For celebrities (above threshold), use fan-out on read — their followers' feeds pull celebrity tweets directly at read time. The feed service merges both sources. Twitter uses ~10,000–50,000 followers as the threshold.

📥 3 · Fan-out on Read (Pull Model)

When a user requests their feed, the feed service fetches the latest tweets from each followed account and merges them into a ranked timeline.

ScenarioFan-out on Read cost
User follows 500 accounts500 DB reads per feed refresh — expensive
Celebrity tweets to 100M followersOne write — very cheap
Dormant user hasn't opened app in a weekNo wasted write — no pre-built cache to maintain

The pull model shines for celebrities and inactive users. It is slow for active users who follow many accounts and need fast feed loads.

💬 5 · WhatsApp at Scale

Scale: 100 billion messages per day, 2 billion users, 50 billion messages stored. Core challenges: reliable delivery, read receipts, and end-to-end encryption.

Core Components

ComponentRole
WebSocket connectionsPersistent TCP connections between clients and WhatsApp servers. Required because HTTP is stateless — servers cannot push to clients without a persistent connection.
Message queueStores messages when recipient is offline. Uses HBase (columnar) for durable message storage.
Delivery receiptsSingle check ✓ = sent to server. Double check ✓✓ = delivered to device. Blue ✓✓ = read by recipient.
ZookeeperTracks which connection server a user is connected to (user → server mapping).

End-to-End Encryption

Signal protocol: Each message is encrypted on the sender's device with the recipient's public key. WhatsApp servers only route ciphertext — they cannot read messages. Keys are exchanged during initial contact via the X3DH (Extended Triple Diffie-Hellman) protocol. This is why WhatsApp cannot comply with law enforcement requests to read messages.

Message Delivery Flow

Group Chat

Server-side fan-out: In a group of N members, when a user sends a message, the server fans it out to all N-1 other members. WhatsApp limits groups to 1,024 members to keep fan-out manageable. Each member's device still decrypts independently using their own key.
