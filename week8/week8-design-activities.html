⚡ Part A — Quiz

Question 1

Kafka guarantees message ordering within a partition. If you need all events from a specific user to be processed in order, what should you do?

  • Use a single-partition topic for the entire topic
  • Use the user's ID as the partition key so all their events hash to the same partition
  • Sort messages by timestamp in the consumer before processing
  • Increase the number of brokers in the cluster
Partition key = user ID. Kafka hashes the key to determine partition. All messages with the same key (user ID) land in the same partition, which is consumed by one consumer in the group — preserving order for that user.
Question 2

What is the primary purpose of a Consumer Group in Kafka?

  • To encrypt messages before consumption
  • To allow producers to batch messages
  • To distribute topic partitions across multiple consumers for parallel processing
  • To replicate data across brokers for fault tolerance
Parallel processing. Each partition is assigned to exactly one consumer within a group, enabling horizontal scaling. If you have 6 partitions and 3 consumers, each consumer reads 2 partitions in parallel. Adding consumers beyond the partition count doesn't help — idle consumers result.
Question 3

An e-commerce platform needs to route order events to different queues based on country: EU orders to one queue, US orders to another. Which is the better choice?

  • RabbitMQ — supports topic exchanges and flexible routing rules
  • Kafka — because it handles higher throughput
  • Both are equally suited for complex routing
  • Neither — use an API Gateway for routing instead
RabbitMQ. RabbitMQ's exchange-binding model supports complex routing patterns (topic exchanges, header-based routing). Kafka's pub-sub model is topic-based — you'd need separate topics per region or consumer-side filtering, which is less elegant for complex routing.
Question 4

A consumer processes the same Kafka message twice due to a restart before committing the offset. Which delivery guarantee applies, and how do you handle it?

  • At-most-once — reduce batch size to avoid this
  • At-least-once — make the consumer idempotent so duplicate processing is safe
  • Exactly-once — this scenario should not happen with Kafka
  • No delivery guarantee applies here
At-least-once + idempotency. When a consumer crashes after processing but before committing the offset, it re-reads and reprocesses the message. The solution is to make the processing idempotent: e.g., use INSERT ... ON CONFLICT DO NOTHING with a unique event ID, so duplicate processing has no effect.
Question 5

What problem does the Outbox Pattern solve?

  • It reduces the number of Kafka brokers needed
  • It allows consumers to read messages faster
  • It compresses messages before they are stored
  • It ensures events are published reliably even if the message broker is temporarily unavailable at write time
Reliable event publishing. Without the outbox, a service might write to its DB successfully but then fail to publish the event to Kafka — causing silent inconsistency. The outbox writes the event to the DB in the same transaction, then a relay reads and publishes it. If the relay fails, it retries from the persisted outbox row.

🖊️ Part B — Design Workshop: Order Processing System

System Requirements

An e-commerce platform processes 10,000 orders per minute at peak. When an order is placed, it must:

  1. Deduct inventory (Inventory Service)
  2. Charge the customer's payment method (Billing Service)
  3. Send an order confirmation email (Notification Service)
  4. Update the analytics dashboard (Analytics Service)

Constraint: If billing fails, inventory deduction must be rolled back. If notification fails, the order should still succeed.

Design questions to answer in pairs

  1. Will you use choreography (events) or orchestration (saga orchestrator)? Why?
  2. Which services should be in the critical path (synchronous) and which can be async?
  3. How many Kafka topics will you create? What are they named?
  4. How do you handle the billing failure and rollback of inventory?
  5. How do you ensure the notification service doesn't send duplicate emails on retry?

🖊️ Part C — Design Workshop: Real-Time Analytics Pipeline

Requirements

A gaming platform needs to display real-time player metrics on an operations dashboard: active players per region, average match duration, and revenue in the last 5 minutes. Events arrive at 500,000 events/second at peak.

Guiding questions

  1. What Kafka topic structure would you use? (One topic vs. many? How many partitions?)
  2. Which stream processing framework would you consider for windowed aggregations? (Apache Flink, Kafka Streams, Spark Streaming)
  3. Where would you store the computed aggregates for the dashboard to read? (Redis? ClickHouse? Elasticsearch?)
  4. How does the dashboard receive updates — polling or WebSockets?
  5. What retention period do you configure for the Kafka topic, and why?

🤝 Part D — Design Review Checklist

  • Kafka vs. RabbitMQ choice justified with a specific reason, not just "Kafka is better"?
  • Partition count reasoned from throughput requirements and consumer parallelism?
  • Delivery guarantee identified (at-least-once) and idempotency mechanism described?
  • Failure rollback strategy explained (compensating transactions, saga pattern)?
  • Consumer group isolation achieved (analytics doesn't slow down billing consumer)?
  • Retention period justified for the business need (replay, debugging, compliance)?

📝 Part E — Reflection

  1. Research: what is "consumer lag" in Kafka, and what metric do you monitor to detect it? What causes high lag?
  2. Research: Apache Flink vs. Kafka Streams — what are the key differences in deployment model and use case?
  3. If you needed to replay the last 24 hours of order events to rebuild a corrupted inventory database, how would you do it with Kafka? What if the events are older than your retention period?
