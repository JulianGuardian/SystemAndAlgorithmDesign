Block 2 – Design at Scale · Week 8

Distributed Messaging & Event-Driven Systems

Apache Kafka · RabbitMQ · Event-Driven Architecture · Delivery Guarantees · Outbox Pattern

🎯 Learning Objectives

  • Explain how message queues decouple producers and consumers, providing buffering and durability.
  • Describe Kafka's core concepts: topics, partitions, offsets, consumer groups, and retention.
  • Compare Kafka (log-based) vs. RabbitMQ (queue-based) and select the right tool for a scenario.
  • Define at-most-once, at-least-once, and exactly-once delivery, and explain how idempotency solves duplicate processing.

📬 1 · Why Message Queues?

ProblemWithout MQWith MQ
Service couplingOrder service calls inventory directly — both must be upOrder publishes event — inventory consumes when ready
Traffic spikesDownstream overwhelmed, requests droppedQueue absorbs spikes — consumer processes at own pace
Service failureIf inventory is down, order failsMessages persist in queue until inventory recovers
ScalabilityOrder service must know all downstream servicesProducers and consumers independently scalable
Core benefits: Decoupling (producers and consumers don't know each other), buffering (absorb traffic spikes), durability (messages survive server restarts), async processing (producer doesn't wait for consumer to finish).

🔥 2 · Apache Kafka

Kafka is a distributed, append-only log. Unlike a traditional queue, messages are not deleted after consumption — they are retained for a configurable period (default 7 days). Multiple consumers can independently read the same messages.

Core Concepts

ConceptDescription
TopicA named stream (like a table name). Producers write to topics; consumers read from topics.
PartitionA topic is split into N partitions for parallelism. Each partition is an ordered, immutable log.
OffsetSequential ID of each message within a partition. Consumers track their own offset — they control their read position.
ProducerWrites messages to a topic. Can specify a partition key (hash determines partition) for ordering guarantees.
Consumer GroupA group of consumers sharing the work. Each partition is assigned to exactly one consumer in the group.
BrokerA Kafka server. A cluster has multiple brokers; partitions are distributed across them for fault tolerance.
Kafka ordering guarantee: Messages within a single partition are ordered. Across partitions, there is no ordering. To guarantee all events from a specific user are processed in order, use the user's ID as the partition key — all their events land in the same partition.

⚖️ 3 · RabbitMQ vs. Kafka

DimensionRabbitMQApache Kafka
ModelMessage queue (push to consumer)Distributed log (consumers pull)
After consumptionMessage deleted (consumed once)Message retained (multiple consumers can re-read)
OrderingFIFO per queueOrdered within partition
ThroughputHigh, but Kafka is higher at scaleVery high (millions of msgs/sec)
RoutingRich routing (exchanges, bindings)Simple pub-sub by topic
ReplayNo — message deleted after ackYes — rewind offset to replay
Best forTask queues, complex routing, RPCEvent streaming, audit logs, data pipelines
Choose RabbitMQ when you need: point-to-point task distribution (e.g., email sending), complex routing (topic exchanges), or request-reply patterns. Choose Kafka when you need: high throughput, event replay, multiple independent consumer groups, or building an event-sourced system.

⚡ 4 · Event-Driven Architecture

Events vs. Commands vs. Queries

TypeMeaningExample
CommandRequest to do something (directed)PlaceOrder(userId, items)
EventNotification that something happened (broadcast)OrderPlaced{orderId, timestamp}
QueryRequest for data (no side effects)GetOrderStatus(orderId)

Choreography vs. Orchestration

Choreography: Each service reacts to events independently. No central coordinator. Loose coupling, but hard to trace the overall flow.

Orchestration: A central saga orchestrator tells services what to do via commands. Easier to understand flow, but the orchestrator is a coupling point.

Outbox Pattern — Reliable Event Publishing

Problem: Writing to DB and publishing an event are two operations — one can fail. If the DB write succeeds but the Kafka publish fails, the event is lost silently.

Solution: Write the event to an outbox table in the SAME DB transaction as the business data. A separate relay process (or Debezium CDC) reads the outbox and publishes to Kafka. If the relay fails, it retries from the outbox — guaranteed at-least-once delivery.

📦 5 · Delivery Guarantees

GuaranteeMeaningHowRisk
At-most-onceDelivered 0 or 1 timesFire and forget; ack before processingMessage loss if consumer crashes
At-least-onceDelivered 1+ timesRetry on failure; ack after processingDuplicate messages — consumer must be idempotent
Exactly-onceDelivered exactly 1 timeKafka transactions + idempotent producersComplex; not always necessary
Idempotency: An operation is idempotent if applying it multiple times has the same effect as applying it once. Example: UPDATE orders SET status = 'shipped' WHERE id = 42 is idempotent — running it 10 times doesn't change anything after the first run. Design consumers to be idempotent to handle at-least-once delivery safely.
Interview insight: When asked "how do you guarantee exactly-once?", the honest answer is: "Use at-least-once delivery + idempotent consumers." True exactly-once is expensive and rarely necessary. Most real systems (Kafka, SQS) operate at-least-once and require idempotent downstream processing.
