Databases at Scale

SQL vs NoSQL · Indexing · Replication · Sharding · CAP Theorem

🎯 Learning Objectives

  • Articulate the differences between SQL and NoSQL and when to choose each.
  • Explain how a B-tree index speeds up queries and what trade-offs it introduces.
  • Describe primary-replica replication and how it improves read throughput and availability.
  • Apply horizontal sharding (partitioning) to distribute data across multiple DB nodes.
  • State the CAP theorem and explain why no distributed database can guarantee all three properties.

🗃 1 · SQL vs. NoSQL

SQL (Relational)NoSQL (Non-Relational)
StructureTables, rows, columns. Fixed schema.Documents, key-value, graph, columnar. Flexible schema.
Query languageSQL (standardized)Vendor-specific (MongoDB MQL, DynamoDB API…)
ACIDYes (full ACID transactions)Usually eventual consistency; ACID optional
ScalingVertical (scale-up) + limited horizontalDesigned for horizontal scale-out
JoinsNative, efficientNo native joins — must denormalize
ExamplesPostgreSQL, MySQL, SQLiteMongoDB, Cassandra, DynamoDB, Redis

When to choose what

Choose SQL when: Data has clear relationships, you need complex queries/joins, financial/transactional data requires ACID, team knows SQL well.

Choose NoSQL when: Data is unstructured or semi-structured, you need horizontal scaling, schema changes frequently, very high write throughput (Cassandra, DynamoDB).
Interview answer: In most system design interviews, defaulting to SQL (PostgreSQL) is correct unless you have a specific reason not to — high write load, need for horizontal shard-scale-out, or a document/graph data model. Always justify your choice.

📇 2 · Indexing

Without an index, a database performs a full table scan — reading every row to find matches: O(n). An index is a separate data structure (usually a B-tree) that pre-organizes a column's values so lookups are O(log n).

Index Trade-offs

Benefit: Reads are O(log n) instead of O(n).
Cost: Every INSERT/UPDATE/DELETE must also update the index → slower writes.
Rule of thumb: Index columns that appear in WHERE, JOIN, and ORDER BY clauses. Avoid indexing columns with low cardinality (e.g., boolean, gender).

Composite Index

An index on (user_id, created_at) can satisfy queries on user_id alone OR (user_id AND created_at), but NOT on created_at alone. The leftmost prefix rule: always place the most selective or most-queried column first.

📋 3 · Replication

Replication keeps copies of data on multiple database nodes. The most common pattern is primary-replica (formerly master-slave).

Benefits of replication:
• Read scalability: Add replicas to handle more read traffic
• High availability: If primary fails, promote a replica
• Disaster recovery: Geographic replicas survive data center outage

Replication lag: Async replication means replicas may be slightly behind the primary. A user who just wrote may not see their write if routed to a replica → "read-your-writes" consistency issue.

🍰 4 · Sharding (Horizontal Partitioning)

When a single database can no longer handle the write load or storage, you shard — split the data across multiple database nodes, each responsible for a subset of the data (a shard).

Sharding Strategies

StrategyHowProCon
Range-basedShard 1: user_id 0-1M, Shard 2: 1M-2M…Simple range queriesHot partition if new users cluster
Hash-basedshard = hash(user_id) % NUniform distributionRange queries span all shards; hard to add shards
Directory-basedLookup table maps key → shardFlexibleLookup table is a single point of failure
Sharding challenges: Cross-shard joins are expensive or impossible. Resharding (changing N) requires migrating all data. Celebrity/hotspot problem: one shard gets all traffic for a popular user.

🔺 5 · CAP Theorem

In a distributed system, you can only guarantee two of three properties simultaneously:

Consistency (C): Every read returns the most recent write or an error.
Availability (A): Every request receives a response (not necessarily the latest data).
Partition Tolerance (P): System continues operating even when network messages are lost.

In practice: Networks fail, so P is non-optional. You must choose between C and A during a partition.
CP systems (PostgreSQL, HBase): return error if they can't guarantee fresh data.
AP systems (Cassandra, DynamoDB): return possibly stale data but always respond.

ACID vs. BASE

ACID (SQL)BASE (NoSQL)
Atomic: all-or-nothing transactionsBasically Available: system always responds
Consistent: always valid stateSoft state: data may be in transition
Isolated: transactions don't interfereEventually consistent: converges over time
Durable: committed data survives crashesTrade-off for higher availability and performance

📋 Week 3 Summary

SQL = ACID, joins, fixed schema NoSQL = scale-out, flexible B-tree index = O(log n) reads Primary-replica = read scalability Hash sharding CAP: choose CP or AP
Decision tree for database choice:
Need complex joins or transactions? → SQL (PostgreSQL)
Need extreme write throughput (millions/sec)? → Cassandra (AP)
Need flexible document schema? → MongoDB (CP)
Need fast key-value lookup? → DynamoDB or Redis
