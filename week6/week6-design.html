Token Bucket in Redis

Python# Pseudocode — Token Bucket using Redis + Lua (atomic)
# Lua executes atomically on Redis server — no race conditions
LUA_SCRIPT = """
local key = KEYS[1]
local capacity = tonumber(ARGV[1])    -- max tokens
local refill_rate = tonumber(ARGV[2]) -- tokens per second
local now = tonumber(ARGV[3])         -- current timestamp

local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
local tokens = tonumber(bucket[1]) or capacity
local last_refill = tonumber(bucket[2]) or now

-- Refill tokens based on elapsed time
local elapsed = now - last_refill
tokens = math.min(capacity, tokens + elapsed * refill_rate)

if tokens >= 1 then
    tokens = tokens - 1
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    return 1  -- allowed
else
    return 0  -- rate limited
end
"""

def is_allowed(redis_client, user_id: str, capacity=10, rate=1) -> bool:
    key = f"rate_limit:{user_id}"
    result = redis_client.eval(LUA_SCRIPT, 1, key, capacity, rate, time.time())
    return result == 1
Why Lua scripts? Without Lua, a check-then-decrement sequence is not atomic — two concurrent requests can both pass the check before either decrements. Lua scripts execute as a single atomic operation on the Redis server.

🌐 4 · Distributed Rate Limiter

When multiple app servers need to share rate limit state, a single Redis node (or Redis Cluster) acts as the central counter.

ArchitectureProsConsUse when
Centralized RedisExact count, simple logicRedis is a single point of failure; latency on each requestHigh accuracy needed (API monetization)
Local counters + syncLow latency; no Redis on hot pathSlightly over-allows during sync intervalInternal services, slight over-allow is OK
Interview tip: When asked "how do you handle Redis downtime?", answer: "Fail open (allow all requests temporarily) to avoid blocking legitimate traffic. Log all requests during the outage for post-hoc analysis and potential billing adjustment." Failing closed (block all) is almost always wrong.
