⚡ Part A — Conceptual Quiz

Question 1

A celebrity with 50 million followers posts a tweet. The system uses fan-out on write. How many cache writes are triggered?

  • 1 — write to the celebrity's own feed cache
  • As many as there are active followers right now
  • 0 — fan-out on write skips celebrity accounts
  • ~50 million — one write per follower's timeline cache
~50 million writes — fan-out on write pushes the new post to every follower's pre-computed feed cache. This is the core write amplification problem of the push model. That's why hybrid approaches skip the push for celebrities and serve their posts on read instead.
Question 2

Redis Sorted Set operation ZRANK leaderboard "player_42" has what time complexity?

  • O(1)
  • O(log n)
  • O(n)
  • O(n log n)
O(log n) — Redis Sorted Sets use a skip list internally. ZRANK, ZADD, and ZRANGE are all O(log n), making them ideal for real-time leaderboards at massive scale.
Question 3

The Token Bucket algorithm allows bursts. What does this mean in practice?

  • Requests are queued and processed in order, never rejected
  • Burst traffic causes the service to scale horizontally
  • If tokens have accumulated (low traffic period), a burst of requests can all pass through until the bucket empties
  • Burst tokens are tokens that represent failed requests
Accumulated tokens allow bursts — if your bucket fills up to 100 tokens during a quiet period, a burst of 100 simultaneous requests all succeed. This is in contrast to the Sliding Window Counter, which enforces a strictly uniform rate at all times.
Question 4

Why does a notification service use Kafka between the notification server and delivery workers?

  • Kafka is faster than HTTP for small payloads
  • It decouples producers from consumers and buffers spikes so workers aren't overwhelmed
  • Kafka provides end-to-end encryption for notifications
  • Kafka automatically deduplicates notification messages
Decoupling and buffering — Kafka absorbs traffic spikes (e.g., a breaking news event) so workers process at their sustainable rate. It also retains messages for replay on worker failure, guaranteeing delivery even when third-party providers (FCM, email) are temporarily down.
Question 5

An idempotency key is used in notification systems to:

  • Prevent the same notification from being sent twice if a worker retries after a failure
  • Encrypt the notification payload for the recipient
  • Track the delivery time of each notification
  • Route the notification to the correct provider (FCM vs APNs)
Prevent duplicate delivery — with at-least-once delivery, a worker may retry after a crash. The idempotency key (e.g., a UUID stored in Redis) ensures the same logical notification is only sent once, even if the job runs multiple times.

🏆 Part B — Design Workshop: Live Gaming Leaderboard

In groups of 2, design a real-time leaderboard for a mobile game with the requirements below. Label all components on the whiteboard and justify every choice.

System Requirements

Users: 50 million registered players, 5 million daily active

Score updates: 200,000 score submissions/second at peak (end of game)

Read traffic: 1 million leaderboard reads/second (players checking top-100)

Leaderboard types: Global all-time · Weekly · Friends-only (up to 500 friends)

Latency targets: Score update <50ms P99 · Leaderboard read <30ms P99

Guided Design Questions

  1. Which Redis data structure do you use for the global leaderboard? What commands handle a score update and a top-100 query?
  2. At 200K updates/second, can a single Redis instance handle the write load? How would you shard the leaderboard?
  3. The weekly leaderboard resets every Monday at midnight. How do you implement the reset without downtime?
  4. The friends-only leaderboard requires knowing a player's friends. Where do you store friendship data, and how do you compute their leaderboard on read?
  5. How do you prevent score manipulation (a player submitting fake scores from the client)?
  6. A score update triggers a push notification to the player who just got overtaken in the top-10. How does this interact with your notification architecture from the lesson?

Notification types to support

• Push notifications (iOS via APNs, Android via FCM) — immediate, for active users

• Email (via SendGrid) — daily digest, marketing, security alerts

• SMS (via Twilio) — OTP verification, critical account alerts only

Design Dimensions to Address

DimensionYour Design Decision
User preference storage (opt-in/opt-out per channel)
Priority queuing (OTP SMS must arrive in <5s; marketing email can wait hours)
Retry strategy when FCM returns a 503
Deduplication (user receives 10 comments in 1 min — send 1 digest, not 10 pings)
Analytics (open rate, click rate, unsubscribe rate)
Handling 50M notifications triggered by a single viral event
